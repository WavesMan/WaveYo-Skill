# OpenAPI 接口文档规范

> 触发时机：新增或修改路由、请求/响应结构、字段命名与类型，需要生成或增量维护
> OpenAPI 3.1 文档时；或需要把文档同步到接口平台（如 Apifox）时必读。
>
> 文档是**面向调用方的契约**，不是代码注释的搬运。凡是调用方能观察到的变化，
> 都必须落到文档里，并留下变更记录。

---

## 1. 用途与触发条件

### 用途

- 从路由与处理器代码**生成或增量更新** OpenAPI 3.1 文档，保证文档与实现一致。
- 接口演进时**不丢历史**：路径/方法变更用弃用标记，字段变更用变更记录，
  让调用方能够看到「改了什么、什么时候改的、该用什么替代」。
- 让文档能被工具消费：导入接口平台、生成客户端、做契约测试时不被解析问题卡住。

### 触发条件

- 新增路由、修改路径或 HTTP 方法
- 请求/响应结构体增删改，含匿名嵌入字段、`json:"-"`、自定义序列化
- 字段重命名、删除、类型变更、必填与可选变更
- 文档与代码不一致被发现（线上返回值与文档对不上）
- 接口平台需要重新导入

### 不触发

- 只读查看文档
- 纯内部重构（调用方不可见的实现调整）
- 只改注释措辞且语义不变

---

## 2. 适用边界

| 属于本专题 | 不属于本专题 |
|---|---|
| 文档结构、路径与方法、schema、示例 | 鉴权实现与权限模型 → 项目认证/授权文档 |
| 字段变更记录、弃用标记 | 数据库表结构与迁移 |
| 文档与实现一致性校验 | 上游依赖错误映射 → `upstream-error-handling.md` |
| 导入接口平台的前置条件 | 分支、提交、PR → `git-workflow.md` |

**三条硬边界**：

1. **文档面向调用方**：不得写入存储类型、表结构、内部序列化机制、服务端拓扑等信息。
2. **不做权限承诺**：文档可以描述鉴权方式，但不能把「前端会校验」写成安全边界。
3. **不静默改协议**：字段改名、类型变更属于对外破坏性变更，必须走变更记录与弃用流程，
   不能靠一次提交悄悄替换。

## 3. 核心规则

### 3.1 文件位置与命名

- 文档统一放在项目约定的文档目录（下文示例用 `docs/api/`），**不与源文件同目录**。
- 一个源文件对应一个文档文件，文件名 = **源文件名 + 后缀**，例如：
  `internal/api/media.go` → `docs/api/media.go.yaml`。
- 目录不存在时先创建；生成前确认目标文件是否已存在（存在则走增量更新）。
- 若文档目录被 `.gitignore` 忽略，**用 `ls`/`dir` 判断文件是否存在**，
  不要用会被忽略规则跳过的搜索方式（Glob / Grep 会漏掉被忽略的文件，导致误判「不存在」而覆盖重写）。

> 项目已有文档目录约定时以项目为准；关键是「一源文件一文件、路径可预测」。

### 3.2 从路由与处理器提取接口

以 Go + Gin 为例（其他框架同构：找路由注册 → 找处理器签名 → 找绑定结构）：

```go
func RegisterTenant(g gin.IRouter, api TenantAPI, handler ...gin.HandlerFunc) {
    group := g.Group("/tenants", handler...)
    group.GET("/:id", web.WrapH(api.getTenant))
}
```

- 路由 `group.GET("/:id", ...)` → `GET /tenants/{id}`，路径参数名 `id`
- 路由函数顶部注释作为接口 `summary` / `description` 来源（如 `// getTenant 获取多租户信息`）
- **框架路径参数写法要规范化**：`:id`（Gin）或 `<id>`（部分路由库）→ OpenAPI 的 `{id}`

### 3.3 参数提取

按处理器签名与实际绑定方式判定参数位置：

| 代码形态 | 文档位置 |
|---|---|
| `_ *struct{}` 或无入参 | 无 query / body |
| `*struct{ Name string \`form:"name"\` }` | query 参数 |
| `*struct{ Name string \`json:"name"\` }` | requestBody（JSON） |
| `struct{ ID string \`uri:"id"\` }` | path 参数 |

其他框架同理：按绑定标签/装饰器判断 query、body、path，不要凭字段名猜。

### 3.4 类型映射规则

文档描述的是**调用方看到的 JSON**，不是语言内部类型：

1. `json:"-"`（或其他序列化排除标记）的字段**不出现在文档中**——调用方永远看不到它。
2. 自定义序列化的类型，以**实际输出**为准：底层是整数但序列化成字符串，就写 `type: string`。
3. 自定义时间类型以实际序列化形式为准（毫秒整数 / RFC 3339 字符串 / 其他），
   不要照抄语言里的时间类型名。
4. 匿名嵌入字段**展开为平级**，不额外增加嵌套层（序列化时会提升到外层）。
5. 指针、可选字段、默认值：写清是 `nullable` 还是有默认值，不要用「应该有值」含糊带过。
6. 枚举、取值范围、单位、时区：能写就写，这是文档最有价值的部分。

### 3.5 字段变更记录（强制）

字段被**修改、删除、重命名、类型变更、必填/可选变更**时，必须记录时间与内容。

- **记录位置**：写在对应接口的 `paths[path][method].description` 里。
  **不要**写进 `info.description`；字段自己的 `description` 只写用途、中文名、取值范围、单位，
  不混入变更历史。
- **格式**：日期后换行，用 Markdown 无序列表列出变更项。

```yaml
paths:
  /messages:
    get:
      description: |
        查询当前登录用户的消息列表，包含内容详情与发送者信息。

        更新说明：
        2026-03-03
        - ref_id 重命名为 target_id
        - status 由 string 改为 integer
```

> 改字段而没写变更记录，等于让调用方在线上自己发现破坏性变更。

### 3.6 路由变更与弃用（强制）

当**实际请求路径或 HTTP 方法**发生变化（如 `GET /tenants/:id` → `GET /tenants/:id/info`，
或 `GET` 改 `POST`）：

1. **旧接口标弃用**：`deprecated: true`，并在 `description` 中说明弃用日期与替代接口。
2. **新接口正常补充**：按常规流程新增定义。
3. **代码中已移除的接口**：文档里的旧接口同样标弃用并注明「代码中已移除」，
   **除非用户明确要求删除**。文档的默认策略是「留痕」，不是「抹掉」。
4. **完成汇报**：每次更新后，向用户汇报本次涉及的弃用接口数量与清单（路径 + 方法）。

**判断标准**：

| 变化 | 处理 |
|---|---|
| 实际路径变更 | 旧接口标弃用 + 新增新接口 |
| 仅 `:id` ↔ `{id}` 表示法转换（URL 与请求方法不变） | **不算变更**，不标弃用 |
| HTTP 方法变更 | 旧方法标弃用 + 新增方法 |
| 接口从代码彻底移除 | 标弃用并注明已移除（除非明确要求删除） |
| 字段/参数变化 | 走 §3.5 变更记录，不涉及弃用 |

```yaml
paths:
  /tenants/{id}:
    get:
      deprecated: true
      description: |
        获取租户信息（旧路径）。
        弃用说明：
        2026-06-12
        - 路由变更为 GET /tenants/{id}/info，请改用新接口
    # 其余定义保留，便于老调用方对照迁移

  /tenants/{id}/info:
    get:
      description: |
        获取租户信息。
```

### 3.7 禁止跨文件 `$ref`

**不要**写 `$ref: "group.go.yaml#/components/schemas/Group"`。
部分接口平台（如 Apifox 的 OpenAPI 导入）无法解析跨文件引用，
被引用的 schema 会退化成只显示 `object` 类型名，字段说明全部丢失。

处理方式（按优先级）：

1. **同一源文件的接口**：schema 定义在该文件内，用文件内引用 `#/components/schemas/Foo`。
2. **不同源文件操作同一实体**：合并到同一个文档文件，用不同 `tags` 区分功能分组。
3. **确实需要复用又不能合并**：把 schema **完整复制**到引用方的 `components/schemas`，
   在复制处注释来源。冗余优于不可解析的引用。

### 3.8 命名与 tag

- **JSON 键必须与真实契约一致**：有序列化标签用标签名，没有就按实际输出保留。
  **不为命名偏好改写公开协议**——文档跟随实现，不是实现跟随文档的审美。
- 保留既有 `snake_case` / `camelCase` / 其他风格，不要在新旧接口间混用两套风格。
- 需要改协议命名时，按破坏性变更处理（§3.5 + §3.6），并取得用户授权。
- **全新生成**时可用 `admin/<中文功能名>` 之类的分组 tag；**增量更新时禁止改已有 `tags`**，
  除非用户明确要求。

### 3.9 面向调用方的描述

- 字段 `description` 写：中文名、用途、取值范围/枚举、单位、时区、是否必填、默认值。
- **不写**：数据库列类型、表名、索引、内部序列化实现、微服务拓扑、内部错误码枚举的私有部分。
- 示例值用**中性且合法**的数据（不要真实手机号、真实密钥、生产域名）。
- 错误响应只描述项目公开的错误契约，不透传上游原始消息（见 `upstream-error-handling.md`）。

### 3.10 公共类型与共享 schema

项目常见的公共参数（分页、时间范围、排序、租户标识等）应抽成 `components/schemas`，
并在各接口内引用：

```yaml
components:
  schemas:
    PagerFilter:
      type: object
      properties:
        page:
          type: integer
          description: 页码，从 1 开始
        size:
          type: integer
          description: 每页数量
        sort:
          type: string
          description: 排序字段，格式 field:asc|desc
    DateFilter:
      type: object
      properties:
        start_ms:
          type: integer
          description: 开始时间（毫秒时间戳，含）
        end_ms:
          type: integer
          description: 结束时间（毫秒时间戳，不含）
```

> 分页/时间字段的实际形状以项目实现为准；这里给的是常见形态，不要照抄字段名与时间单位。

## 4. 实施方法（生成与增量维护）

### 4.1 工作流程

1. **定位源文件**：找到目标路由注册文件与处理器，确认文档目标路径。
2. **提取路由**：路径、方法、路径参数名；`:` / `<>` 参数写法规范化为 `{name}`。
3. **提取参数**：query / body / path，追踪结构体定义，**展开匿名嵌入字段**。
4. **确认目录与文件**：创建目录；用 `ls` 判断目标文件是否存在（见 §3.1 忽略规则提醒）。
5. **生成或增量更新**：
   - 不存在 → 全新生成（可用标准 tag 分组）
   - 存在 → 对比代码变更，增量更新；**保留已有 tags**；字段变化补变更记录
6. **处理弃用**：路径/方法变了就标 `deprecated: true` 并写替代接口，不删旧定义。
7. **自检**：YAML 可解析、`$ref` 可在文件内解析、必填标记与实现一致、变更记录已写。
8. **汇报**：本次新增/修改/弃用的接口清单（路径 + 方法）+ 弃用数量。

### 4.2 校验手段

| 检查 | 方法 |
|---|---|
| YAML 语法与规范 | 用 OpenAPI 校验器（Swagger Editor、`redocly lint`、`spectral` 等） |
| 引用可解析 | 确认所有 `$ref` 都是文件内 `#/components/...` 或可解析的本地文件 |
| 字段与实现一致 | 抽样调用接口，对比返回 JSON 的键名、类型、空值形态 |
| 必填与可选 | 与实现中的校验规则（binding/validator）对照 |
| 弃用留痕 | 旧路径仍在文档中且带 `deprecated: true` + 替代说明 |

> 「YAML 能打开」不等于「文档正确」；至少跑一次校验器，并抽样比对真实响应。

### 4.3 同步到接口平台（可选，需授权）

把文档导入 Apifox / Postman / SwaggerHub 等平台属于**对外写入**，需满足：

1. **授权**：用户明确要求本次同步，或项目规则已明确授权自动同步。
   仅有 token、项目 ID，或「先更新本地文档」的指令，**不构成上传授权**；已有明确授权不重复确认。
2. **凭据与目标**：从环境变量读取 token，项目 ID 已从用户指定或项目规则核实。
   **只检查是否存在，不输出凭据值**。
3. **路径**：从项目根目录确认目标文件存在，脚本与文件参数都用**绝对路径**；
   不要先切到脚本目录再把相对路径当项目路径。
4. **结果判定**：记录平台返回的导入结果；**脚本退出码 0 不等于接口全部导入成功**，
   要看导入报告（失败条目、schema 警告）。
5. 不满足条件时只完成本地文档，并说明未同步的具体原因（不是「忘了」）。

## 5. 常见错误

| 反模式 | 后果 | 正确做法 |
|---|---|---|
| 改了响应字段，文档没动 | 调用方按旧契约解析，线上报错 | 字段变更同步文档 + 变更记录 |
| 把变更历史写进 `info.description` | 全局信息被污染，调用方看不到具体接口的变更 | 写进对应 `paths[path][method].description` |
| 路径变了直接删旧接口 | 老调用方无迁移依据 | 标 `deprecated: true` + 写替代接口 |
| `:id` 改 `{id}` 就标弃用 | 产生大量假弃用，噪音淹没真变更 | 表示法转换不算变更 |
| 跨文件 `$ref` | 平台导入后 schema 退化成 object | 文件内引用 / 合并文件 / 复制 schema |
| 按语言内部类型写 `type` | 文档类型与实际 JSON 不符 | 以序列化结果为准 |
| 照抄数据库类型与表名 | 泄露实现细节 | 只写调用方需要的语义 |
| 增量更新时重排/改写 tags | 平台分组错乱，历史丢失 | 增量不动已有 tags |
| 文档字段名与实现不一致 | 客户端生成后调用失败 | 跟随真实序列化键名 |
| 脚本退出 0 就当导入成功 | 失败条目被忽略 | 核对导入报告 |
| 用 Glob/Grep 判断被忽略的文档是否存在 | 误判不存在 → 覆盖已有文档 | 用 `ls`/`dir` 检查 |

## 6. 验收清单

**结构**

- [ ] 文档位于项目约定目录，一源文件一文件，路径可预测
- [ ] 路径参数统一为 `{name}`，与实现的实际路由一致
- [ ] 所有 `$ref` 可在文件内解析，无跨文件引用
- [ ] 公共 schema（分页/时间等）已抽取并在接口内引用

**内容**

- [ ] 请求与响应字段与真实序列化输出一致（含 `json:"-"` 排除、嵌入字段展开）
- [ ] 自定义序列化类型按实际 JSON 输出书写
- [ ] 必填/可选、枚举、单位、时区、默认值已写明
- [ ] 描述面向调用方，无表结构、内部类型、拓扑信息
- [ ] 示例值中性合法，无真实凭据与生产地址

**演进**

- [ ] 字段变更已写入对应接口 description 的「更新说明」
- [ ] 路径/方法变更的旧接口已标 `deprecated: true` 并写明替代接口
- [ ] 增量更新未改动已有 `tags`
- [ ] 已汇报新增/修改/弃用接口清单

**校验**

- [ ] YAML 通过校验器（语法 + OpenAPI 规范）
- [ ] 抽样比对真实响应，键名与类型一致
- [ ] 如已同步平台，导入报告已核对，未把退出码当成功
